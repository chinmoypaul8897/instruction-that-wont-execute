### 2. Goldens BEFORE the parser — hard rule 4
Pick **three** FR documents by hand. Read their `<AMDPAR>` elements with `grep`/`sed` only — no project code. Write down, by hand, for each: every instruction, which section it belongs to, and its `(operation, anchor, designation)` triple.

### 3. Build the carry-forward attributor
The algorithm is specified in `CONTEXT.md` §8 — implement **that**, not your own reading. Iterate in document order, maintain `current_section`, attribute lettered sub-instructions to the last-named section, and count anything attributable to nothing as **unattributable** rather than guessing.

⚠️ **Q8 applies here.** Element names differ between government formats. **Assert your extractor against a known-positive input before believing any zero it prints.** A zero that means "wrong tag name" looks exactly like a zero that means "nothing there".

### 4. Measure completeness — the gate
Per `CONTEXT.md` §8's definition, reported **globally and per FR document**.

**Pre-registered branches — take these, do not deliberate:**

| Completeness | Action |
|---|---|
| **≥ 0.90** | Proceed. Report the figure. |
| **0.80 – 0.90** | Proceed, **and** compute the restricted pool: only FR documents with per-document completeness ≥ 0.90. Publish the restriction as a named rung with its count. Report both figures. |
| **< 0.80** | The attributor is a documented failure. **Do not tune it to pass.** Report the number, write the failure up in `PROGRESS.md`, and continue to step 5 anyway — the yield measurement is still worth having. |

*A predecessor pilot ran at 0.46 because its extractor read only lead-ins. Only ~42% of AMDPARs name a section.*

### 5. ⭐ THE PAIR-YIELD MEASUREMENT — the most valuable thing in this chunk

**This is the project's largest unknown and nothing has measured it.**

The eval set needs **≥ 42 pairs**. A pair is one defect section plus a **count-matched sibling**: another section amended by the *same* FR document with the *same number of amendatory instructions*, carrying no defect note.

Compute and report:

- For each of the 85 defect sections: how many sections did its FR document amend in total?
- Of those, how many have **exactly the same instruction count** and no defect note?
- **YIELD = the fraction of defect sections with ≥ 1 count-matched sibling**
- **PROJECTED PAIRS = 85 × yield** — report this number plainly against the 42 target
- Also report the yield under **±1 instruction** matching, clearly labelled as a *looser* rule that we are **not** adopting — it tells the architect how much headroom exists if exact matching proves too strict

**Do not adopt the looser rule. Do not relax exact matching.** Report both and let the architect decide. Relaxing the match to inflate n is exactly how a predecessor project died.

Commit as `docs/evidence/ch02-attributor/pair-yield.md` with the generating script.
