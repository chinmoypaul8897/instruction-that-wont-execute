D1  permutation_null RESTORES THE TRUE LABELS BY ASSUMPTION, NOT BY SNAPSHOT

    src/bscript.py lines ~249-251 restore with:
        for a, b in pairs:
            by_id[a]['label'] = 'WILL_FAIL'
            by_id[b]['label'] = 'WILL_EXECUTE'
    i.e. it ASSUMES pair[0] is the positive. `free_permutation_null` does the
    right thing - it snapshots `labels` on entry and restores from that. The
    two functions disagree about how to be safe.

    pairs given as (negative, positive) - a VALID matching of the same pair:
      labels before  {'neg': 'WILL_EXECUTE', 'pos': 'WILL_FAIL'}
      labels after   {'neg': 'WILL_FAIL', 'pos': 'WILL_EXECUTE'}
      corrupted      True   <<< the caller's data was silently relabelled

    the diagnostic null over the same rows, for contrast:
      labels before  {'neg': 'WILL_EXECUTE', 'pos': 'WILL_FAIL'}
      labels after   {'neg': 'WILL_EXECUTE', 'pos': 'WILL_FAIL'}
      corrupted      False

    NOT LIVE TONIGHT: docs/evidence/ch04-scorer/run_bscript.py's
    `reconstruct_pairs` always emits (positive, negative), so the assumption
    holds for the shipped run. tests/test_score.py's restore test also passes
    pairs in that order, so no test would catch the reversal.
