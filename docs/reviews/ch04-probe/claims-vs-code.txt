CLAIM 2  GOOD.md section 5, pre-registered and frozen:
           "The observed labelling is one of the draws, so p can never be 0."
         src/bscript.py module docstring, point 2:
           "The observed statistic is included in its own null. A permutation
            test that excludes it can return p = 0, which is not a probability
            any finite permutation test can produce."

  TRUE in EXHAUSTIVE mode - itertools.product contains the all-keep draw.
  In SAMPLED mode the draws are independent coin flips, so the all-keep draw
  appears with probability 2^-k per draw. The shipped run uses k = 41 pairs
  and 2000 SAMPLED draws: 2^-41 = 4.547e-13 per draw. The claim does not hold
  there, and `p_value = at_least / len(draws)` carries no +1 correction.

  DIRECT CHECK on the SHIPPED configuration - is the observed labelling
  (the all-keep draw) actually among the 2000 draws at seed 20260831?
    k = 41 pairs, n_permutations = 2000 -> mode 'sampled', 2000 draws
    all-keep draw present : False
    all-swap draw present : False
    -> the observed labelling is NOT one of the draws.

  Constructed counterexample where p ACTUALLY comes out 0.0 -
  20 pairs, positives all 1.0, negatives all 0.0, so ONLY the all-keep and
  all-swap draws (2 of 2^20) can reach the observed 1.0, and 200 sampled
  draws contain neither:
    mode                     sampled
    n_draws                  200
    observed best CV acc     1.0000
    draws >= observed        0
    p_value                  0.0
    p_value == 0.0           True   <<< a finite permutation test just
                                      produced p = 0, which GOOD.md section 5
                                      and bscript.py both say cannot happen
    conventional (1+k)/(1+n) 0.004975124378109453

  The SHIPPED run was not bitten - 471/2000 draws >= observed, p = 0.2355 -
  because the B-script is near chance. The claim is still false as written,
  and it is frozen in GOOD.md where hard rule 5 forbids editing it.

  tests/test_score.py::test_SD_p_value_can_never_be_zero uses 2 pairs and
  n_permutations=64, which takes the EXHAUSTIVE branch. The mode the project
  actually runs in is not covered by that test:
    the test's own call -> mode 'exhaustive', p 0.5000

         returns a field named `target_power`.

    power=0.50 -> min_discordant 6  gap 7.3171 pp  target_power reported 0.50
    power=0.80 -> min_discordant 6  gap 7.3171 pp  target_power reported 0.80

    power=0.00 -> min_discordant 6  gap 7.3171 pp  target_power reported 0.00
  -> `power` changes NOTHING. It is echoed into the output as `target_power`

     carries "target_power": 0.8 next to "min_detectable_gap_pp": 7.317.

  Also: min_discordant_all_one_way does not depend on n at all -
